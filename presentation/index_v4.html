Silver design

Insert-only 3NF with deterministic hash keys

hk = sha2(concat_ws('|', source_system, original_pk), 256)

-- SAP order 0004000123  → hk a91f…  (always)
-- JDE order 00001-100042 → hk 7c2e…  (always)

-- no UPDATE / DELETE ever issued:
new version  ⇒  new row (effective_ts)
"current"    ⇒  view: row_number() over (partition by hk
                       order by effective_ts desc) = 1

Why this wins

  • Deterministic across reloads & environments — same input, same key, no lookup tables
  • Streaming-friendly — append-only writes, no MERGE contention
  • Audit for free — full history is just the table
  • Gold assembles by key — facts join dims on hk, no surrogate pipeline
  • record_hash detects no-op updates; quarantine + batch_log on every run

Entity resolution — the honest MDM tier LIVE

norm_name    = trim(regexp_replace(upper(trim(customer_name)), r'\s+(INC|LLC|LTD|CORP|CO|GMBH|AG|SA)\.?$', ''))
norm_country = upper(trim(country))
customer_key_mdm = sha2(concat_ws('|', norm_name, norm_country), 256)

customer_hk stays the stable per-source-system FK grain every fact joins on; customer_key_mdm is the actual cross-source match key — a deterministic exact-match tier (normalized name + country), with probabilistic/fuzzy matching (Zingg/Splink) named as the production upgrade path, not built. Verified live 2026-08-14: 1,001 rows in, 1,001 distinct keys out, 0 collapsed — honestly, that number proves the key computes and is unique per row, not that the matching logic resolves duplicates, since this build's synthetic data was never generated with overlapping real entities across SAP/JDE/QAD to test against. That's a data-generation limit on what this demo can prove, not a logic gap in the key itself.

DV2.0 payoff · docs/DATA_VAULT_PIT_BRIDGE.md

Two query-assist tables turn "cheap to store" into cheap to query too

pit_customer — point-in-time

Grain: one row per (snapshot_date, customer_hk). Daily spine from first customer version to today — equality join, no BETWEEN range scan.

-- as-of join: 2 equality joins, zero range scans
SELECT l.label_date, c.customer_name, c.country
FROM   labels l
JOIN   pit_customer p
       ON p.customer_hk = l.customer_hk
      AND p.snapshot_date = l.label_date
JOIN   silver.customer c
       ON c.hk = p.customer_hk AND c.effective_ts = p.as_of_ts;
  • Leakage-free ML training — features never see labels' future
  • Reproducible month-end reporting — re-run January in July, get January's truth
  • Audit evidence — which region row-filter applied on a given date

bridge_order_fulfillment — lifecycle bridge

Grain: one row per current order, pre-joined to shipment + invoice hash keys (NULL until each stage exists) — one join instead of walking the lifecycle.

-- order-to-cash cycle time + backlog, one table, one GROUP BY
SELECT source_system,
  avg(datediff(invoice_date, order_date)) AS o2c_days,
  count_if(NOT is_shipped)                AS backlog
FROM   bridge_order_fulfillment
GROUP  BY source_system;
  • Order-to-cash cycle time, no 3-table join for analysts or Genie
  • Backlog dashboards from a WHERE clause on two booleans
  • NL-friendly — one join path, no hallucination risk

Both are batch materialized views in gold_dlt.py, recomputed per run — derived, safe to CREATE OR REPLACE; truth stays in Silver history. validate.py checks 13 (PIT freshness) and 14 (bridge FK integrity) gate both in CI.

Governance · how it's actually wired, not just the policy

Row filters & masks live in the pipeline definition, not a bolt-on GRANT

The function — pulled live from information_schema.routines today

CREATE FUNCTION acme_gold.sec.region_filter(source_system STRING)
RETURN is_member('admins')
   OR is_account_group_member('data_engineer')
   OR is_account_group_member('exec_readonly')
   OR (is_account_group_member('sales_analyst_europe')   AND source_system='SAP')
   OR (is_account_group_member('sales_analyst_americas') AND source_system IN ('JDE','EBS'))
   OR (is_account_group_member('sales_analyst_emea')     AND source_system='QAD')
   OR (source_system='D365');  -- CRM rows open to all, PII masked separately

CREATE FUNCTION acme_gold.sec.mask_customer_name(name STRING)
RETURN CASE WHEN is_member('admins') OR is_account_group_member('data_steward')
       THEN name ELSE concat(left(name,2),'*****') END;

Two-layer check, deliberately: is_member('admins') is a workspace-level escape hatch (kept the owner's own visibility while account groups didn't exist yet); is_account_group_member(...) is the account-level check UC actually recommends — confirmed live today: this session's principal is a workspace admin (is_member('admins')=true) but resolves false on every is_account_group_member(...) call, since no account groups exist yet. That gap is exactly what's blocked below.

The hard-won lesson

First attempt: ALTER TABLE ... SET ROW FILTER against a DLT-materialized table → rejected ("expects a table but is a view"). DLT publishes materialized views under the hood; row filters/masks can't be bolted on after the fact.

Fix: declare governance inside the pipeline definition itself —

@dlt.table(row_filter="ROW FILTER acme_gold.sec.region_filter ON (source_system)")
def fact_sales_orders(): ...

-- dim_customer.customer_name gets a MASK in the same publish schema DDL

Verified live in information_schema; validate.py checks 8–9 both PASS. GRANTs to the actual groups are staged in security/unity_catalog_policies.sql — blocked on account-admin group creation (PRINCIPAL_DOES_NOT_EXIST), not a design gap.

Threat model · docs/DASF_ALIGNMENT.md

The agent fleet, scored against Databricks' own AI Security Framework

DASF v1.1: 55 risks across 12 components. This platform is a hosted-LLM consumer — a tool-using client of the Anthropic API — which maps onto Component 9 (Model Serving / Inference Requests) and Component 10 (Inference Responses), not the model-training components that don't apply here.

DASF riskstatusevidence
9.1–9.9 · prompt injection, unbounded tool access, unvetted inputs covered Model's only tool is read-only run_sql; hard-guarded allowlist (SELECT/WITH/SHOW/DESCRIBE, single statement, no semicolon); every call and result logged to audit.agent_runs
9.10 · excess data exposure via job identity open gap Job identities currently read broadly across catalogs; scoped, account-group-based identities are designed (security/unity_catalog_policies.sql) but blocked on the same account-group provisioning gap as RBAC
10.1–10.2 · unscreened generated output, PII leakage in responses open gap Reports/digests in audit.agent_reports have no automated PII or quality screening before landing — a human reads them, nothing programmatic does yet
9.10 (write path) · agent-initiated data corruption covered No agent has DDL/DML access; the one agent that emits SQL text (product_creator) validates it through a regex allowlist + forbidden-verb denylist before executing, and falls back to a hand-written view on any gate failure

Two gaps named on purpose, not hidden: a documented risk register with two open items and a remediation path is what a security review actually wants — not a claim of perfection.

Agentic AI architecture

Ten agents, one platform — each owns a different part of the build

TRIGGERS — Lakeflow task (15-min cron) · events (DQ breach webhook, schema drift, job fail, PR open) · user NL request (marketplace)
ORCHESTRATOR — Claude agent: multi-step reasoning · tool use · code generation · self-correction TOOLS — Databricks MCP (SQL/DDL, Jobs, Pipelines) · GitHub MCP (read, PR) · Asset Bundles CLI · Slack/email · web-fetch smoke tests

DQ Monitor + RCA

owns: Bronze→Silver gates · audit schema
  • Runs the 10 DAMA-dimension checks; writes dq_results
  • In-line RCA on any failure: first bad batch, blast radius
  • Files a structured RCA report every run

DQ Root-Cause (deep)

owns: cross-check correlation, depends on DQ Monitor
  • Reads latest failing checks from dq_results
  • Correlates against batch_log ⨝ source_registry
  • A second, deeper pass — not a duplicate of the first

Pipeline Healer

owns: pipeline-failure triage
  • Scans pipeline events via the Databricks SDK
  • Classifies: schema drift · bad records · infra · code
  • Drafts type-specific remediation, never executes it

Lineage Doc

owns: auto-generated lineage docs
  • Builds edges from live cfg.layer_mappings
  • Attempts system.access.table_lineage, degrades gracefully
  • Output via agent_reports only — a job container can't write to git

Schema Evolution

owns: cfg.layer_mappings · Bronze contract
  • Diffs Bronze information_schema vs. active mappings
  • Drafts versioned mapping-row INSERT proposals
  • Says "no action needed" for intentionally-unmapped columns

Ingestion Registrar

owns: replication_sources.yaml validation
  • Allowlists pattern, region, target-catalog shape
  • Cross-checks against cfg.source_registry
  • Never calls the deploy script itself

Data Product Creator

owns: Gold → Products output ports
  • NL prompt → SQL → secure view in acme_products
  • Regex allowlist + forbidden-verb gate before executing
  • Falls back to a hand-written view on any gate failure

Vector / Content

owns: Gold AI zone · semantic search
  • Rebuilds customer_narratives from dim + facts
  • QA-reviews samples for retrieval-relevant specificity
  • Index refresh is a separate infra step, outside this job

Deployment Gate

owns: CI/CD verification
  • Runs the same 14 checks as validate.py — imported, not duplicated
  • Classifies regression vs. known/tracked gap
  • Issues PROMOTE / HOLD; a human merges

Operational Intel

owns: platform-wide observability
  • Daily digest: volume, freshness, backlog, DQ failures
  • Drills into anomalies with read-only SQL
  • Plain-language report for domain leads

Decision log · docs/JUSTIFICATION_NOTES.md · 2 of 3

The modeling choices trade object count for query simplicity

#decisionwhyalternatives rejected
4Insert-only Silver, SHA-256 hash keys Deterministic keys across 3 ERPs (system|pk); full history for free; merge-free = fast streaming writes SCD2 with MERGE — familiar, but update-heavy, slower streams, key drift risk · Identity surrogate keys — compact joins, but non-deterministic across reloads/environments
5DV2.0 methodology, not DV2.0 objects (3NF Silver + hash keys) Hash keys play the hub-key role, insert-only versions play satellites, PIT/bridge materialize in Gold — without hub/link/sat table explosion for a single-domain pilot Full raw vault (hubs/links/sats) — max auditability, defensible at enterprise scale-out, but 3–4× the tables/pipelines · One Big Table / plain Kimball star — fastest to first dashboard, loses deterministic keys and history-by-default
10PIT as a materialized daily spine (pit_customer) Equality joins (snapshot_date, hk) replace BETWEEN range scans; one blessed as-of path kills ML label leakage; reproducible month-end reports Query-time AS OF / range joins — zero storage, but every consumer rewrites (and mis-writes) temporal logic · SCD2 dim with valid_from/valid_to — familiar to BI, but needs UPDATE, breaking insert-only Silver
11Bridge as pre-joined lifecycle keys (bridge_order_fulfillment) Order→shipment→invoice in ONE join for O2C cycle time, backlog flags, and Genie; NULLs mark incomplete stages honestly Multi-hop joins in the BI/semantic layer — no extra storage, but every tool re-encodes join paths · Denormalize into a wide fact — fastest reads, but grain explosion and full reload on late-arriving stages
