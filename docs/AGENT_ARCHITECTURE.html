Agent control model

Six platform agents live in agents/ and share one contract, defined once in agents/agent_core.py and imported by every agent script. The design principle: the platform never depends on a model being up. Deterministic work always runs; an LLM reasoning pass is strictly additive.

Two-phase execution contract

  1. Deterministic phase (always runs) — checks, table builds, drift scans, corpus rebuilds. Produces the agent's artifact (a table write, a report row) with or without a model available.
  2. Reasoning phase (conditional) — if an Anthropic API key resolves (env ANTHROPIC_API_KEY, else Databricks secret agents/anthropic_api_key), a Claude tool-loop runs on top of the deterministic evidence and produces the narrative report. Without a key, the agent logs "deterministic mode" and still completes.

Guardrails (deliberate, load-bearing for the design)

  • One tool, read-only: the model's only action surface is run_sql, hard-guarded in safe_sql() to a single statement starting with SELECT / WITH / SHOW / DESCRIBE. Anything else (a semicolon, a write verb) is rejected before it reaches Spark and logged as "REJECTED non-read-only query".
  • All writes happen in deterministic framework code, after the reasoning pass — the model narrates and proposes (e.g. a schema-mapping INSERT as SQL text in its report), it never executes a write directly.
  • Full audit trail: every run is logged to acme_bronze.audit.agent_runs (run_id, agent, mode, status, started_at, finished_at, decision_log — every tool call + result summary, truncated to 8,000 chars). Narrative output is persisted to acme_bronze.audit.agent_reports (report_id, agent, created_at, title, body).
  • Human gate: agents open PRs / propose fixes; they never auto-merge to main (agents/README.md).
  • Tool budget: MAX_STEPS = 12 turns. If exhausted mid-investigation, the loop forces one final turn with tool_choice: none and the instruction "write your final report NOW from evidence already gathered" — so a truncated investigation still yields a usable report instead of dangling mid-tool-call.

These guardrails are mostly about write-safety. For the separate question of what stops an agent from hallucinating — inventing numbers, tables, or conclusions not backed by a real query — see docs/AGENT_RELIABILITY_GUARDRAILS.md, which also compares this design against Anthropic's current published standards for agent reliability.

# Content-QA Report -- acme_gold.ai.customer_profile_text (Customer Profile Narratives)

Corpus: 1,001 narratives, all with distinct customer_hk and distinct text. Length 142-179 chars
(avg ~176). Composition: 500 SAP / 501 JDE. Countries skew MX (186), US (158), CA (157), then EU.

## CRITICAL -- a data artifact is being embedded as a business signal

Every one of the 501 JDE (Americas Metals) customers shows 100% of orders unshipped (backlog =
order count), vs. SAP customers averaging a 30% backlog ratio and none fully unshipped. Root cause
confirmed in bridge_order_fulfillment:

| source_system | bridge rows | shipped | unshipped |
|---|---|---|---|
| SAP | 5,000 | 3,478 | 1,522 |
| JDE | 5,000 | 0 | 5,000 |
| QAD | 3,000 | 0 | 3,000 |

JDE (and QAD) have no shipment records populated -- is_shipped is false for 100% of rows. So "Has
open fulfillment backlog awaiting shipment" on all 501 JDE customers is a pipeline coverage gap,
not a real backlog. Embedding this will flood any "who has shipping backlog / stuck orders"
retrieval with 501 false positives and bury the genuinely-backlogged SAP accounts.

Action: Do not emit backlog language for source systems whose fulfillment feed is unshipped-only.
Suppress or flag the signal until JDE/QAD shipment data lands.

## QAD customers appear missing from the corpus
The narrative set is only SAP+JDE (1,001), but bridge_order_fulfillment contains 3,000 QAD order
rows. QAD-sourced customers may be absent from dim_customer/narratives entirely. Left unverified
(tool budget) -- recommend confirming corpus completeness against all three source systems.

## Retrieval-relevance issues in the narrative template
1. Internal jargon a seller would never query ("source system SAP / JDE") -- drop or move to
   metadata.
2. No recency -> churn cannot be phrased. Add a recency phrase (e.g. "Last ordered 2026-02, ~3
   months ago; ordering has slowed").
3. Backlog phrased as a raw count, not seller language -- add natural synonyms + USD value.
4. Revenue formatting -- no separators/rounding, no time window.
5. Cosmetic: "order(s)" pluralization.

## What's fine
No bare hash keys/opaque codes inside profile_text; currency units stated; country ISO code
present and consistent.

Bottom line: structure and units are acceptable, but the corpus currently embeds a
fulfillment-data gap as a fake backlog signal on half the customers, omits the recency needed for
churn search, and leans on ETL jargon. Fix the JDE/QAD backlog handling first.
